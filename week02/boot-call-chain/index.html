从 QEMU 启动到 kernel_main 的完整调用链

不少同学反映"文件之间的调用关系连不起来"——根源通常不是某一行代码看不懂， 而是没分清编译期（每个文件各自变成 .o）、链接期（linker.ld 把符号拼成真实地址）、 运行期（QEMU 真正执行 bl / jr）这三层。下面先过一遍三层关系，再给出 boot/start.S → kernel/main.c → kernel/printk.c / lib/string.S 的完整运行期调用图，对应 docs/02/lab.md 的 Task3–Task5。

先分清三个阶段

"调用关系连不上"九成发生在这里：以为 bl clear_bss 是文本意义上的跳转，其实它要等链接器把地址填进去才成立。

01 · 编译

各文件互不知情

start.S、main.c、string.S… 分别独立编译成 .o。此时 bl kernel_main 里的 kernel_main 只是一个待解析的符号名，编译器不检查它在别的文件里是否存在。

gcc -c start.S -o build/boot/start.o
→
02 · 链接

ld 把符号拼成地址

kernel/linker.ld 决定各段的摆放地址；ld 收集所有 .o 里 .globl 导出的符号（clear_bss、memset…），把每处引用替换成真实地址，同时算出 __bss_start/__bss_end。

ld -T kernel/linker.ld *.o -o minios.elf
→
03 · 运行

PC 真正跳转

QEMU 把 ELF 加载进内存，PC 设为 ENTRY(_start) 指定的地址。从这一刻起，bl / jr 才是真正发生的函数调用与返回——下面的图画的就是这一层。

qemu-system-loongarch64 -kernel minios.elf

运行期调用图

按源文件着色；实线箭头 = 真实发生的 bl 调用 / jr $ra 返回，虚线箭头 = 链接期符号引用或本次课不会被执行的路径。

声明 ↔ 实现对照

对应 Task5：跨文件调用能连起来，靠的是"头文件声明 + .S/.c 里 .globl 导出 + Makefile 把两边都编进 SRCS"三件事同时成立。

头文件（声明）实现文件关键符号
include/string.hlib/string.Smemset, memcpy, strlen
include/printk.hkernel/printk.cprintk, printk_udec, printk_hex
include/uart.hkernel/printk.cuart_putc, uart_puts, UART0_BASE
（无头文件，脚本本身）kernel/linker.ld__bss_start, __bss_end, ENTRY(_start)

三个常见误区

1

__bss_start / __bss_end 不是函数

它们是 kernel/linker.ld 里的位置标号，只表示地址，没有可执行的指令体。只能用 la.global 把地址取到寄存器里当数据用，不能像 clear_bss 一样 bl 过去。

2

halt: 本次课不会被执行到

kernel_main 自己的最后一步就是 while (1) { idle 0; }，程序永远停在 C 函数里，不会"执行完"返回到 _start 里 bl kernel_main 之后的 halt 循环。

3

跨文件的调用是编译 + 链接一起完成的

start.S 里的 bl 之所以能跳到 main.c、string.S 里的符号，是因为对方用 .globl（C 里默认非 static）导出了这个名字，并且 Makefile 的 SRCS_S/SRCS_C 把这个文件一起编译链接了进来。少列一个文件就会在链接期报 undefined reference。
