## 第 0 节　为什么要专门讲"打印"这件小事

在应用程序里，`printf("hello\n")` 是一行代码就能用的库函数。但在内核/裸机环境里，
没有操作系统、没有 libc、甚至没有"文件"这个概念，"把一个字符显示出来"这件事
要从硬件寄存器一路搭到"系统调用接口"，中间经过好几层抽象：

```text
应用层调用          printk("hello\n")
                        │
输出子系统层         uart_puts()  →  uart_putc()
                        │
硬件访问层           往固定地址写一个字节（MMIO）
                        │
真实硬件             UART 芯片把字节移进移出、变成电平信号
```

第 1 次课我们直接"裸写地址"把 Hello 打出来，这是最快但最不安全、最不可扩展的做法。
本次课要做两件事：

1. **把裸写地址整理成一个像样的"输出子系统"**（分层、加 volatile、处理换行）；
2. **把这个子系统包装成一个"系统调用"** `sys_write(fd, buf, len)`，
   这是内核对外提供服务的标准姿势，而不是谁想打印就直接摸硬件。

这两件事分别对应"驱动程序应该长什么样"和"内核服务接口应该长什么样"，
是后面所有课程（文件系统、进程调度、用户态/内核态隔离）的地基。

> **生活化类比**：这就像一家刚开业的小饭馆。第一天老板自己既配菜又端盘子又收银
> （对应"裸写地址"），能开张但完全没法扩张。本次课要做的，一是把后厨流程理顺
> （洗菜→切配→炒菜分工明确，对应"输出子系统分层"），二是在前厅设一个统一的
> 点餐窗口——顾客不用跑进后厨点名要某个厨子做菜，只需要对着窗口说"几号桌，
> 要什么"，后厨内部怎么分工顾客不用关心（对应"系统调用"这层统一入口）。

## 第 1 节　MMIO：CPU 如何"跟硬件说话"

### 1.1 什么是 MMIO

MMIO（Memory-Mapped I/O，内存映射 I/O）是指：把外设（UART、定时器、中断控制器……）
的控制/数据寄存器映射到 CPU 的地址空间里，**读写这些地址在指令层面和读写内存完全一样**
（`ld`/`st` 指令），但实际效果是跟硬件对话，而不是访问 RAM。

这意味着：

```c
volatile unsigned char *uart = (volatile unsigned char *)UART0_BASE;
*uart = 'A';   // 语法上是"给一个地址赋值"，效果上是"让 UART 发送字符 A"
```

`UART0_BASE` 就是 UART 数据寄存器在地址空间里的固定位置，具体数值由芯片/平台手册
（或课程给定的 `include/uart.h`）决定，**不能凭空编造**，必须以代码为准。

> **生活化类比**：把地址空间想象成一整栋公寓楼的门牌号。大部分门牌号后面住的是
> "普通住户"（RAM，你敲门/写信只是单纯的信息存取）；但其中有几个特殊门牌号
> 其实是"传达室"（UART 寄存器）——你往传达室的信箱里塞一张纸条，效果不是
> "纸条存起来了"，而是"传达室的人立刻把内容广播出去"。CPU 并不知道也不关心
> 门牌号背后是普通住户还是传达室，它只会做同一个动作：往这个地址写。

### 1.2 为什么必须加 `volatile`

编译器在优化代码时，会假设"连续两次给同一个变量赋值，中间没人读它，
那第一次赋值是没用的，可以删掉"。对普通内存这个假设成立，
但对 MMIO 地址是**致命错误**：每一次写，硬件那头都会真实响应一次
（比如"发送一个字符"），即使地址的值表面上"没变化"。

`volatile` 告诉编译器：**这块内存的内容可能被"程序看不见的外部因素"改变，
或者每次访问本身就有副作用，因此每一次读写都必须真实发生，不能被优化、
合并、重排、缓存进寄存器。**

对照理解：

| 场景 | 不加 volatile 会怎样 |
|---|---|
| 普通局部变量 `int x` | 优化器可能把它一直放寄存器里，没问题 |
| MMIO 寄存器地址 | 优化器可能把"重复写同一地址"直接删掉，导致硬件收不到指令 |
| 中断处理程序会修改的全局变量 | 主循环里读到的可能是寄存器里的"旧值缓存"，永远等不到变化 |

> **生活化类比**：编译器优化就像一个"精打细算"的秘书。你让秘书"给张三发一份文件，
> 再给张三发同一份文件"，秘书会想："反正张三收到的最终内容一样，我只发一次得了"——
> 对普通文件这么做没问题。但如果这两次"发文件"其实是"按一下门铃"（每按一次，
> 门铃都会真的响一声），秘书擅自省掉一次，后果就是该响的门铃没响。`volatile`
> 就是明确告诉秘书："这个动作，每一次都必须真的执行，不许你自作主张合并"。

### 1.3 一次写操作在汇编层面长什么样

```asm
# $a0 = 待发送字符, $t0 = uart 基址
    st.b    $a0, $t0, 0      # 把 $a0 的低 8 位写到 [$t0 + 0]
    jr      $ra
```

`st.b` 是"store byte"，把一个字节写到内存地址；因为 `$t0` 指向的是 UART 寄存器
而不是普通 RAM，这一条指令的效果就是"让 UART 发一个字节"。这也是第 4 次课
"MMIO = store" 这句话的具体落地。

## 第 2 节　从"能打印一个字符"到"输出子系统"

### 2.1 三层职责划分

```text
printk(s)                          【格式化/业务层：谁都可以调用】
  └─ uart_puts(s)                  【逐字符遍历 + 换行处理：与具体设备耦合较松】
       └─ uart_putc(c)             【单字节 MMIO 写：与硬件寄存器强耦合】
            └─ *(volatile u8*)UART0_BASE = c
```

这样分层的好处：以后如果换一块开发板、串口控制器不一样，理论上只需要改
`uart_putc` 这一层，`printk`/`uart_puts` 完全不用动——这正是第 12 次课
"板级迁移"要考察的能力。

> **生活化类比**：这三层很像"写信—送信"的分工。你（`printk`）只管把内容写好；
> 邮局分拣员（`uart_puts`）负责按规则整理信件（比如"信纸翻页"要同时做"换页+回到
> 页首"）；投递员（`uart_putc`）负责把信塞进具体某一个信箱。如果小区的信箱样式
> 换了（换了一块开发板），只需要投递员换个动作，写信人和分拣员的流程完全不受影响。

### 2.2 为什么 `\n` 要补一个 `\r`

终端上"另起一行"其实是两个独立动作：

- `\n`（Line Feed，换行）：光标垂直下移一行；
- `\r`（Carriage Return，回车）：光标回到本行行首。

在类 Unix 系统里，文本文件约定只用 `\n` 表示换行，但那是"文件格式"层面的约定；
真正的物理终端/串口设备遵循的是更早的电传打字机（Teletype）习惯，**只发 `\n`
只会往下移一行，不会回到行首**，于是屏幕上出现"阶梯状"的错位输出。

所以 `uart_puts` 在遇到 `\n` 时，要先手动发一个 `\r`，再发 `\n`：

```c
if (ch == '\n')
    uart_putc('\r');
uart_putc(ch);
```

这是驱动层为了适配"哑终端"语义做的补丁，属于串口编程的老传统，
Windows 文本文件里 `\r\n` 混用的历史根源也在这里。

> **生活化类比**：想象一台老式打字机。"换行"（`\n`）只是把纸卷往上转一格，
> 打字头本身还停在刚才那一列；如果不"回车"（`\r`）把打字头拨回最左边，
> 下一行的字就会从上一行结束的位置开始打，越打越往右偏，跟楼梯台阶一样。
> 所以每次"另起一行"，实际上是"回车+换行"两个动作缺一不可，这是从机械打字机
> 年代传下来的习惯，现在的串口终端依然照单全收。

### 2.3 教学取舍：先跑通，再讲严谨

当前的 `uart_putc` 直接写数据寄存器，**没有检查硬件是否"准备好接收下一个字节"**。
这是本课刻意的简化：先让大家看到"MMIO 能工作"，轮询等待的严谨版本放到 §3 讲，
选做任务里再实现。

## 第 3 节　16550 风格 UART 的轮询发送

### 3.1 为什么真实驱动不能"无脑硬写"

UART 硬件内部有一个很小的发送缓冲区（FIFO），CPU 写数据的速度远快于串口线上
实际"移出"一个字节的速度（受波特率限制，比如 115200 bps）。如果缓冲区满了
还继续写，多出来的数据会丢失或者产生未定义行为。

因此工业上通用的做法（源自 16550 兼容 UART 芯片的编程模型）：**写数据前先看
状态寄存器（LSR，Line Status Register）里"发送保持寄存器是否为空"这一位，
为空才写，不为空就原地等。**

> **生活化类比**：UART 发送就像往一个只能放一件快递的小前台货架上放包裹，
> 快递员（串口硬件）以固定速度把货架上的包裹取走送出去。如果你（CPU）不管
> 货架上有没有东西，一股脑不停地把新包裹摞上去，多出来的包裹要么掉地上摔坏、
> 要么直接盖住了旧包裹——这就是"数据丢失"。所以正确做法是先看一眼货架
> （读 LSR 状态位）："空的吗？空了我才放下一件，没空我就在旁边等一会儿再看"。

### 3.2 轮询发送的骨架

```asm
# 示意：$t0 = uart 基址；LSR_OFF / THR_OFF / TX_EMPTY_MASK 为课程/手册给定常量
wait_tx:
    ld.bu   $t1, $t0, LSR_OFF      # 读状态寄存器（无符号字节加载）
    andi    $t1, $t1, TX_EMPTY_MASK # 只保留"发送空闲"这一位
    beqz    $t1, wait_tx           # 该位为 0（未空闲）就继续等
    st.b    $a0, $t0, THR_OFF      # 空闲了，把字符写进发送寄存器
    jr      $ra
```

这段代码把第 3、4、5 次课的三个知识点串在了一起：

- **逻辑运算**（`andi` 做位掩码，只关心某一位状态）；
- **访存指令**（`ld.bu` 读、`st.b` 写，均为字节粒度）；
- **循环结构**（`beqz` 条件跳转回到标号 `wait_tx`，构成"忙等待"循环）。

具体的偏移量 `LSR_OFF`、`THR_OFF` 以及掩码 `TX_EMPTY_MASK` 属于芯片/平台细节，
**必须以课程代码或平台手册为准**，允许查阅 16550 寄存器表帮助理解，但不能编造
数值直接用到实验里。

### 3.3 轮询 vs 中断驱动（预告）

轮询发送简单但会"占用 CPU 傻等"；工程上更常见的是**中断驱动**：CPU 写完就去
干别的事，等硬件准备好了主动打断 CPU（发中断）通知它继续。这是后续课程
（中断/异常处理）要覆盖的内容，本课先建立"为什么需要检查状态位"这个概念即可，
思考题里会问到这一点，先留个印象。

> **生活化类比**：轮询就像你去楼下取快递,但驿站还没到货,你选择**站在柜台前
> 不停问"到了吗到了吗到了吗"**,什么别的事也不干,直到到货为止——简单，
> 但极度浪费你的时间。中断驱动则是你把手机号留给驿站,自己回家该干嘛干嘛，
> 等快递真的到了，驿站主动打电话通知你（发中断），你再下楼去取。CPU 也是一样，
> 中断驱动能让它在等待期间去做别的有意义的事情，而不是"傻站着干等"。

## 第 4 节　设备抽象：为什么要有 `struct uart_device`

### 4.1 当前实现的问题

现在 `uart_putc` 里硬编码了 `UART0_BASE`；一旦要支持第二块板子、或者同一块板子
上有多个串口，代码就得到处复制粘贴、改地址，极易出错且难以维护。

### 4.2 分层抽象思路（本课只讨论，不要求实现）

```c
struct uart_device {
    unsigned long base;                                  // 平台相关：基址
    void (*putc)(struct uart_device *dev, char c);        // 平台相关：具体发送方式
};
```

这里体现的是一种常见的驱动设计模式：**把"平台相关的东西"（基址、初始化流程、
寄存器偏移）收拢进一个结构体和一组"驱动实现函数"，把"平台无关的东西"
（`printk` 的格式化逻辑、`uart_puts` 的字符串遍历、`\n`→`\r\n` 的转换规则）
留在上层，通过函数指针间接调用下层。**

这样以后换板子，只需要提供一份新的 `struct uart_device` 实例和对应的
`putc` 实现，上层代码一行都不用改——这就是"接口稳定，实现可替换"的思想，
也是操作系统里"驱动模型"的雏形。本课不要求写出完整实现，重点是理解这个
分层动机，为第 12 次课的板级迁移做铺垫。

> **生活化类比**：这有点像手机充电器的"万能接口"思路。不同品牌的插座、
> 不同国家的电压标准是"平台相关"的东西，被收进一个个"转换头"里；你的手机
> 只认准一个统一的充电口（`putc` 这个接口），到了不同国家换个转换头插上去
> 就能用，手机内部的充电逻辑完全不用改。`struct uart_device` 干的就是
> "转换头"这个角色——把"这块板子具体怎么发信号"的细节封装起来，上层只管
> 调用统一接口。

## 第 5 节　从"打印函数"到"系统调用"：为什么要多这一层

### 5.1 普通函数调用 vs 系统调用

到目前为止，`printk` 是"谁想调用就直接调用"的普通函数（`bl` 跳转），
调用者需要知道函数的确切地址/符号名，编译时就绑死了。

**系统调用（syscall）**解决的是另一个问题：当内核要对外（尤其是对运行在
更低权限的用户态程序）提供服务时，不能让用户态代码知道内核函数在内存里的
具体地址（既不安全，也不稳定——内核一升级地址就变了）。于是内核提供一个
**统一、编号化的入口**：

```text
用户态：把"我要哪个服务"的编号放进某个寄存器，把参数放进另外几个寄存器，
        然后触发一次"陷入"（本课教学简化为直接调用 dispatch 函数）
              │
内核态：根据编号去查表/分支，找到对应的服务函数并执行，
        执行完把结果放回约定的寄存器
```

调用者只需要记住"编号 + 参数槽位"这套**稳定的接口约定**，完全不需要知道
内核内部函数叫什么名字、在哪里。这就是"内核服务接口"和"普通函数调用"
的本质差异——**接口的稳定性 > 直接碰到具体实现**。

> **生活化类比**：普通函数调用像是"直接闯进朋友家里翻他自己的抽屉"——前提是
> 你俩关系够铁、你知道抽屉在哪（知道函数地址）。而系统调用更像"打政务大厅的
> 服务热线 12345"：你不需要知道具体哪个科室、哪位工作人员在处理你的诉求，
> 你只需要拨通固定号码，说清楚"我要办哪项业务"（系统调用号）和"相关材料"
> （参数），热线内部会帮你转接到正确的窗口。就算大厅内部重新装修、换了办公室
> 位置（内核代码更新、函数地址变化），你拨打的号码和说话的方式完全不用变。

### 5.2 为什么要"统一入口"而不是给每个服务一个裸函数地址

如果每个内核服务都直接暴露一个固定地址让用户态跳过去调用，会有几个问题：

1. **地址会变**：内核代码一改、一重新编译，函数地址就变了，用户态程序全部失效；
2. **没有校验点**：任何人跳到任意内核地址执行，内核完全没有机会做权限检查、
   参数合法性检查；
3. **难以扩展**：新增服务、废弃服务都会牵一发动全身。

而"统一入口 + 编号分发"把所有校验逻辑集中在一个地方（`syscall_dispatch`），
新增服务只需要加一个编号和一个分支，接口本身（怎么陷入、参数放哪、
返回值放哪）完全不变。这是思考题第 3 题的核心答案方向。

> **生活化类比**：如果一栋写字楼里每个部门都各自开一个对外的侧门，任何人
> 想找哪个部门就直接从对应侧门闯进去，那么保安根本没法统一管控谁能进、
> 带了什么东西进去，出了事也很难追查是从哪个门进来的。改成"所有人必须走
> 前台大堂、刷卡登记、说明来意再被引导到对应楼层"，安检和登记就能集中在
> 一个地方完成——`syscall_dispatch` 就是这个"前台大堂+安检口"。

## 第 6 节　sys_write 逐行精读

### 6.1 函数签名与语义

```c
long sys_write(int fd, const char *buf, size_t len)
{
    if (fd != 1 && fd != 2)
        return -1;
    for (size_t i = 0; i < len; i++) {
        if (buf[i] == '\n')
            uart_putc('\r');
        uart_putc(buf[i]);
    }
    return (long)len;
}
```

逐行拆解：

- **`fd`（file descriptor，文件描述符）**：本课只接受 `1`（stdout，标准输出）
  和 `2`（stderr，标准错误），这是照搬 Unix/Linux 的约定，其余一律视为非法。
  真实系统里 fd 是一套通用的"资源句柄"机制，本课先接触最基础的两个编号。
- **参数合法性检查在最前面**：这是系统调用的标配动作——**任何跨越信任边界
  的输入都要先校验**，不合法直接拒绝并返回错误码，绝不能先执行一半才发现
  参数有问题。思考题第 4 题问的就是这个道理的延伸（用户指针校验）。
- **复用 `uart_putc`，没有重复实现 MMIO 写**：`sys_write` 只是在 §2 输出子系统
  之上包了一层"接口壳"，真正干活的还是原来那套逻辑。这体现了"边界在接口，
  不在重复造轮子"的设计原则。
- **成功返回写入长度，失败返回 `-1`**：这也是 Unix 系统调用的通用惯例
  （成功返回非负值，失败返回负数错误码），`write(2)` 在真实 Linux 里就是
  这个套路的完全体。

> **生活化类比**：`sys_write` 很像快递公司的"收件窗口"。窗口第一件事是核对
> 面单（"这是要寄到 1 号线还是 2 号线？其他线路一律拒收"，对应 `fd` 校验），
> 面单不对直接退回，不会先收下包裹再发现地址是错的。核对通过之后，真正
> "打包装车"的动作（`uart_putc`）窗口自己并不重新发明，还是交给后面熟悉的
> 装车流程去做，窗口只负责收件登记和最后告诉你"寄出了多少件，还是寄丢了"。

### 6.2 `printk` 与 `sys_write` 的关系

```text
printk(s)  ≈  sys_write(1, s, strlen(s))
```

也就是说，`printk` 可以理解为"永远往 fd=1 写、自动计算长度"的 `sys_write`
便民封装。二者的差异在于：`printk` 是内核内部直接调用的普通函数，不经过
"编号分发"这一层；而 `sys_write` 是通过 `syscall_dispatch` 编号调用的
"正式对外服务"。本课教学阶段为了降低难度，`sys_write` 也是在内核内部
直接被调用/测试的，还没有真正打通"用户态陷入内核态"的完整链路，
这一点在 §7 会说明。

## 第 7 节　分发器 syscall_dispatch 与寄存器约定

### 7.1 分发逻辑

```c
long syscall_dispatch(long nr, long a0, long a1, long a2)
{
    if (nr == SYS_WRITE)
        return sys_write((int)a0, (const char *)a1, (size_t)a2);
    return -1;
}
```

`nr`（number，系统调用号）决定了要执行哪个服务；本课只登记了一个
`SYS_WRITE`，遇到未知编号统一返回 `-1`。这是一个最小但完整的"分发表"雏形，
真实内核里这里通常是一个跳转表（数组下标或 `switch`），随着系统调用数量
增多而扩展——这正是思考题第 4 题（拓展题）问的方向。

### 7.2 参数与返回值的寄存器约定

| 含义 | 教学放置位置 |
|---|---|
| 系统调用号 `nr` | `$a7`（或课程约定的寄存器） |
| 参数 1 / 2 / 3 | `$a0` / `$a1` / `$a2` |
| 返回值 | `$a0` |

用户侧准备参数的示意代码：

```asm
    li.d      $a0, 1              # fd = 1（stdout）
    la.global $a1, msg            # buf = 字符串地址
    li.d      $a2, 13             # len = 13
    # li.d $a7, SYS_WRITE         # 系统调用号放进约定寄存器
    # syscall  或  bl 到内核封装   # 具体"陷入"方式按课堂方案选择
```

需要特别说明的是：**教学阶段为了降低难度，允许先在内核内部直接调用
`syscall_dispatch`**（相当于跳过了"用户态触发陷入指令、CPU 切换到内核态"
这一整套机制），重点是先把"稳定的编号和参数槽位"这套约定立住。
真正的用户态/内核态隔离、`syscall` 指令触发的异常处理流程，会在后续课程
（异常与中断、特权级）里补齐。这也是为什么讲义反复强调
"接口稳定 > 一次上完整用户态隔离"。

> **生活化类比**：`$a7`/`$a0`–`$a2` 这几个寄存器就像政务大厅表格上"固定填写栏"：
> 第一栏永远填"办理事项编号"，第二到第四栏永远填"申请人信息、材料 A、材料 B"，
> 不管你今天办的是身份证还是营业执照，表格格式不变，工作人员一看就知道该往
> 哪个栏位找什么信息。本课先把"表格格式"（寄存器约定）定下来，"是否要真的
> 排队安检"（用户态陷入内核态的完整机制）留到后面课再补。

## 第 8 节　与 Linux `write()` 的类比（帮助理解，非考察内容）

真实 Linux 上的 `write(int fd, const void *buf, size_t count)` 和本课的
`sys_write` 在"形状"上几乎一模一样：

- 都是 `fd + buf + len` 三元组；
- 都是"成功返回写入字节数，失败返回负的错误码"；
- 都要先做参数校验（Linux 内核还要校验 `buf` 这个指针来自用户态、
  地址范围合法，不能让用户态传一个指向内核内存的指针进来"越权读写"，
  这正是思考题第 4 题问的"用户指针校验为何关键"）。

本课的实现是一个极度简化的教学版本（只支持两个 fd、没有真正的用户态隔离、
没有指针校验），但**接口设计的骨架和真实系统是一致的**，理解了这一套，
再看真实内核代码会觉得眼熟很多。

> **生活化类比**：这就像小朋友学骑自行车先用带辅助轮的儿童车——车架、龙头、
> 脚踏板的基本结构和真正的自行车完全一样，只是暂时少了"完全靠自己保持平衡"
> 这一部分难度（对应"用户态隔离"和"指针校验"）。等基本骨架的操作练熟了，
> 摘掉辅助轮（补齐用户态/内核态隔离机制），就能直接骑上真正的"整车"。

## 第 9 节　小结：本课新增的心智模型

1. **MMIO**：地址不再只是内存，读写它就是在跟硬件对话，必须 `volatile`。
2. **分层驱动**：`putc`（硬件相关）→ `puts`（换行适配）→ `printk`（业务层），
   越往上越与具体硬件无关。
3. **轮询等待**：写硬件前先看"忙不忙"，是最基础也是最常见的硬件同步方式。
4. **设备抽象**：把"平台相关的量"收拢进结构体+函数指针，为可移植性铺路。
5. **系统调用的本质**：用"编号 + 固定参数/返回值寄存器槽位"替代"直接暴露
   函数地址"，换来接口的稳定性和可校验性。
6. **`sys_write` 只是对既有输出路径的一层薄封装**，真正的字符输出逻辑
   仍然来自 §2 的输出子系统——理解"分层"和"复用"比记住某一行代码更重要。
