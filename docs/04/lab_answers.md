## Task1 有效地址与状态变化

### 问题 1：分析 `ld.d $t1, $sp, 16`

1. **动作/宽度：** 这是一条 load 指令，从内存里加载 **64 位（8 字节，双字）** 数据，写入通用寄存器。
   与 `mem_copy_d` 里的 `ld.d $t0, $a0, 0`（`lib/mem_fp.S` 第 27 行）是同一条指令、同一种数据宽度，
   只是换了目的寄存器和偏移量。
2. **操作数角色：**
   - `$t1`：**目的寄存器**，存放本次加载的结果；
   - `$sp`：**基址寄存器**，提供一个基地址（这里恰好是栈指针，但对 `ld.d` 而言它只是"一个装了地址的寄存器"，指令本身不关心这个地址逻辑上是不是栈）；
   - `16`：**立即数偏移**（`si12` 范围内的常数），单位是字节，加到基址上形成有效地址。
3. **有效地址计算：**

   ```text
   EA = $sp + 16 = 0x80001000 + 0x10 = 0x80001010
   ```

4. **执行后的状态变化：**
   - **变化的寄存器：** 只有 `$t1`，变成从地址 `0x80001010` 读出的 64 位值。
   - **不变的寄存器：** `$sp` 本身不变（`ld.d` 不带自增/自减变体，不修改基址寄存器）。
   - **不变的内存：** `0x80001010` 处的内存内容不变——这是一条 **load**，数据流向是"内存 → 寄存器"，不会反过来改内存。

### 问题 2：`mem_byte_add3_self` 参考实现

**`include/mem_fp.h` 新增声明**（紧跟 `mem_byte_add3` 之后）：

```c
/* 学生自己实现：base[2] = base[0] + base[1]（练习用，参数约定同 mem_byte_add3） */
void mem_byte_add3_self(unsigned char *base);
```

**`lib/mem_fp.S` 补全（3 行 TODO）：**

```asm
/* ---- 学生练习：自己实现 base[2] = base[0] + base[1] ---- */
    .globl mem_byte_add3_self
mem_byte_add3_self:
    move    $t0, $a0        /* 题目设定基址在 $t0，这里先从 $a0 搬过去 */
    ld.bu   $t1, $t0, 0     /* t1 = base[0]（零扩展） */
    ld.bu   $t2, $t0, 1     /* t2 = base[1]（零扩展） */
    add.d   $t1, $t1, $t2
    st.b    $t1, $t0, 2     /* base[2] = t1 的低 8 位 */
    jr      $ra
```

> 与 `mem_byte_add3`（第 32–38 行）逻辑完全一致，只是入口多了一步 `move`，中间用的寄存器从
> `$t0/$t1`（临时结果）换成了 `$t1/$t2`（因为 `$t0` 已经被 `move` 占用来装基址）——**只要不
> 覆盖还要用的值，用哪个 `$t` 系列寄存器都可以**，这也是这道题唯一容易踩坑的地方。

**`kernel/main.c` 接入调用**（紧跟 `mem_byte_add3(byte_area);` 那段之后）：

```c
{
    unsigned char my_area[3] = {200, 100, 0};
    mem_byte_add3_self(my_area);
    printk("mem byte_add3 (self): 200+100 = ");
    print_i64_dec(my_area[2]);
    printk("\n");
}
```

**真实 `make clean && make && make run` 新增输出：**

```text
mem byte_add3 (self): 200+100 = 44
```

**回答：**

1. 代码见上（3 行：两次 `ld.bu`、一次 `add.d`、一次 `st.b`，共 4 行——TODO 注释写的"3 行左右"含加法在内可以是 3~4 行，写成 4 行完全正确）。
2. `44` 的由来：`200 + 100 = 300`（十进制），二进制是 `1 0010 1100`（9 位）。`st.b` 只把源寄存器
   **最低 8 位**写到内存里，也就是截掉第 9 位（那个进位的 `1`），剩下 `0010 1100 = 0x2C = 44`
   （等价于 `300 mod 256 = 44`）。`st.b` 不做溢出检查、也不会因为结果超过一字节就自动把
   `base` 数组"扩宽"——**它只是一条无条件截断低 8 位再写内存的指令**，数组本身还是学生在 C 里
   声明的 `unsigned char[3]`，指令层面根本不知道、也不关心"数组"这个概念。
3. 一致。取数（两次 `ld.bu`，都是无符号零扩展）→ 相加（`add.d`，64 位加法，不会因为源是字节
   宽度就限制加法本身的位宽）→ 写回（`st.b`，截断低 8 位）三步顺序和寄存器使用方式与
   `mem_byte_add3` 完全相同，唯一差别只是多了一步把基址从 `$a0` 搬到 `$t0`（因为题目设定"基
   址已经在 `$t0`"这个前提，而 ABI 调用进来时参数实际在 `$a0`）。

## Task2 有符号与无符号加载

真实 `make run` 输出（与 lab.md §4 一致）：

```text
mem ld.b  (signed)   0x80 -> -128
mem ld.bu (unsigned) 0x80 -> 128
```

**回答：**

- **为什么同一字节读出不同的 64 位值：** `ld.b` 和 `ld.bu` 从内存取出的 8 位比特串完全相同
  （都是 `1000 0000`），差别只在**扩展到 64 位寄存器时怎么补高 56 位**——`ld.b` 是符号扩展，
  按这个字节的最高位（符号位 `1`）把高位全部补 `1`，结果是 `0xFFFFFFFFFFFFFF80`（有符号读为
  `-128`）；`ld.bu` 是零扩展，高位统一补 `0`，结果是 `0x0000000000000080`（`128`）。这是加载
  类指令特有的"决定往上补什么"的问题，`ld.d`/`ld.w`（已经是寄存器原生宽度或不需要再扩展）不
  存在这个选择。
- **为什么 store 家族没有 `st.bu`：** store 的方向是"寄存器 → 内存"，只需要把源寄存器**低若干位
  的原始比特模式截断**后写出去（`st.b` 只取低 8 位），这个截断操作本身**不依赖也不需要区分**
  源寄存器里的值是按有符号还是无符号语义使用的——同一个比特串截断后写到内存，结果都一样。
  "有符号 vs 无符号"这件事只在**向上扩展**（load，需要决定高位补 0 还是补符号位）时才有意义，
  向下截断（store）没有对应的歧义，所以指令集里不需要 `st.bu` 这种变体。

## Task3 LL/SC 纸面推演（填表）

### 表 1：只有一个执行流，没人插队

| 步骤 | 指令 | 执行前 `a` | `$t0` | `$t1` |
|---|---|---|---|---|
| 1 | `ll.w $t0, $a0, 0` | 3 | **3** | — |
| 2 | `addi.w $t1, $t0, 1` | **3** | **3** | **4** |
| 3 | `sc.w $t1, $a0, 0` | **3** | **3** | **1**（成功，写回后 `a` 变为 4） |
| 4 | `beqz $t1, retry` | — | — | **1** |

**回答：** 第 3 步执行完 `$t1 = 1`，表示 `sc.w` **成功**（没人插队，链接没被打断，`t1` 的值真的
被写入了内存）。`a` 最终变成 **4**。

### 表 2：B 在 A 做完 `ll.w`/`addi.w`、还没做 `sc.w` 时插了一脚

| 步骤 | 执行者 | 动作 | 这一步之后 `a` 的值 | A 的 `$t0` | A 的 `$t1` |
|---|---|---|---|---|---|
| 1 | A | `ll.w $t0, $a0, 0` | 3 | 3 | — |
| 2 | A | `addi.w $t1, $t0, 1` | 3 | 3 | 4 |
| 3 | B | 完整跑一遍 `ll.w`/`addi.w`/`sc.w` | **4**（B 读到 3、算出 4、成功写回） | 3（不变） | 4（不变） |
| 4 | A | `sc.w $t1, $a0, 0` | **4**（不变，A 的 sc.w 失败，没有真正写入） | 3 | **0**（失败标志） |
| 5 | A | `beqz $t1, retry` | 4（不变） | 3（不变） | 0（不变，跳转到 `retry`） |
| 6 | A | 若失败，重新执行第 1–3 条指令一遍 | **5**（重新 `ll.w` 读到 4→`t0=4`，`addi.w`→`t1=5`，这次没人插队，`sc.w` 成功写回） | 4 | 1（成功标志） |

**回答：**

- 第 3 步之后 `a` 变成 **4**（B 完整、不受干扰地把 `a` 从 3 改成了 4）。
- 第 4 步 A 的 `sc.w` 会**失败**：A 在第 1 步 `ll.w` 时给地址 `$a0` 建立了"链接"，但第 3 步
  B 成功执行了 `sc.w`，**对同一块内存做了写入**，这就把 A 的链接**打断**了（不管打断者写的是
  什么值、写没写回原值，只要期间发生过对该地址的写入，链接就失效）。所以 A 的 `sc.w` 检测到
  链接已断，**拒绝真正写内存**，只把目的寄存器 `$t1` 置成 **0** 表示失败，`a` 保持 B 写入的值
  不变。
- 失败后 A 重新跑一遍第 1–3 条指令（这次没人再插队）：重新 `ll.w` 读到当前 `a=4`，`addi.w`
  算出 `5`，`sc.w` 顺利成功写回，`a` 最终稳定在 **5**。

### 概念问答参考答案

- **LL/SC 主要解决的问题：** 并发场景下"读—改—写"这一整套操作的**原子性**问题（也叫"更新丢失"
  问题）——如果只用普通的 `ld`+`add`+`st`，两个执行流可能都读到旧值、各自算出"旧值+1"、再各自
  写回，其中一次更新会被另一次覆盖掉、凭空丢失。对照表 2：正是因为 A 的"链接"在第 3 步被 B
  的写入打断，A 的 `sc.w` 才会**主动失败**而不是盲目写回一个基于过期数据算出的结果，逼着 A
  重新读最新值再算一遍，从而保证两次"+1"都真正生效，不会有一次被覆盖。
- **`DBAR` 解决的问题：** 内存访问的**顺序性/可见性**问题——保证屏障前后的访存操作，按程序
  指定的先后顺序真正被其他核心/设备观察到，防止流水线乱序执行、缓存或写缓冲区重排导致"别人
  看到的读写先后顺序"和程序里写的顺序不一致。这和 LL/SC 解决的问题**不是一类**：LL/SC 管的是
  "多个执行流同时改同一个变量时，更新会不会互相覆盖丢失"（原子性），`DBAR` 管的是"一串访存指令
  被别人观察到的先后顺序对不对"（顺序性），两者可以同时需要，也可以只需要其中一个。
- **`IBAR` 与 `DBAR` 作用对象的区别：** `DBAR` 作用于**数据访存**（普通的 load/store）的顺序；
  `IBAR` 作用于**取指流**，用来保证"之前对指令/代码所在内存区域的修改"（比如自修改代码、运行
  时生成代码）在之后取指执行时确实可见、按顺序生效——简单说就是"数据屏障 vs 指令（取指）屏障"
  的区别，两者屏蔽的是流水线里不同的两条通路。

### 第三步：位模式搬运 vs 数值转换（标注）

```asm
movgr2fr.w    $fa0, $a0      # 搬位模式
ffint.d.w     $fa0, $fa0     # 转换数值

ftintrz.w.d   $fa0, $fa0     # 转换数值
movfr2gr.s    $a0, $fa0      # 搬位模式
```

- `movgr2fr.w`：只是把 `$a0` 里 32 位的**原始比特模式**原样搬进 `$fa0`，不做任何数值上的解释
  或换算——如果 `$a0=7`（即比特串 `0x00000007`），搬过去之后 `$fa0` 存的就是这串比特，而不是
  "浮点数 7.0"对应的 IEEE754 编码。
- `ffint.d.w`：**转换数值**——把 `$fa0` 里当前存的比特模式**按 32 位有符号整数来解释**，再真正
  计算出对应的双精度浮点数值，重新按 IEEE754 规则编码写回 `$fa0`。
- `ftintrz.w.d`：**转换数值**——把 `$fa0` 里的双精度浮点数值，按**向零舍入**（`rz` = round
  toward zero，即直接砍掉小数部分，不管是正数还是负数都朝 0 的方向截断，例如 `3.9→3`、
  `-3.9→-3`）转换成 32 位整数，结果仍然存在 `$fa0` 里（还是浮点寄存器，只是里面现在放的是整
  数值的位模式）。
- `movfr2gr.s`：只是把 `$fa0` 低 32 位的**原始比特模式**原样搬进通用寄存器 `$a0`（`.s` 后缀表
  示按 FPR 的 32 位宽度搬，不涉及数值换算）。

**为什么只执行 `movgr2fr.w` 得不到数值意义上的 `7.0`：** `movgr2fr.w` 只是"换了个寄存器文件
放同一串比特"，它不知道、也不关心这串比特应该被解释成"整数 7"还是"某个浮点数"。整数 `7` 的比特
模式是 `0x00000007`；而按 IEEE754 binary32 编码的浮点数 `7.0`（`1.75 x 2^2`）的比特模式是
`0x40E00000`——两者完全不同。只把 `0x00000007` 原样塞进浮点寄存器，如果直接当浮点数解读，
得到的是一个指数域全 0 的**极小的非规格化数**（接近 0），根本不是 `7.0`。必须再执行
`ffint.d.w` 做真正的**数值转换**（识别出原始比特是"整数 7"，重新计算并生成"浮点数 7.0"该有的
比特模式），才能得到数值上正确的 `7.0`。真实串口验证（`fp_int_to_double(7)` 再转回整数）：

```text
float int->double->int: 7 -> 7
```

（往返一致，说明 `movgr2fr.w+ffint.d.w` 与 `ftintrz.w.d+movfr2gr.s` 确实是一对可逆的"数值
转换"，而不是简单的位搬运。）
