## 第 0 节　为什么"代码流会被打断"值得专门讲一次课

第 1–8 次课里，代码的执行路径永远是"我方主动发起"的：调用一个函数（`bl`）、
跑一个循环、发起一次系统调用（`sys_write`），都是程序自己决定"接下来去哪"。

从本课开始，要面对另一种情况：**代码流可能被"打断"**，而且打断分两种：

```text
同步异常（exception）：CPU 自己在执行某条指令时触发的，比如 break 指令、除零、缺页
异步中断（interrupt）：外部事件通知的，比如定时器到点了、串口收到一个字节
```

> **生活化类比**：正常调用像你主动打电话给同事安排工作，说完挂断，流程完全在你
> 掌控之中。异常像你自己不小心被绊倒——是你自己的动作引发的，摔倒的瞬间和位置
> 是确定的。中断则像开会时手机突然响了——是外部事件打断你，跟你正在做什么、
> 讲到第几句话完全无关，随时可能发生。

这两种"打断"都要经过同一套硬件机制（本课程平台上是共享同一个 `EENTRY` 入口），
但对代码提出的要求不一样：异常发生时至少知道"是哪条指令引发的"，中断可能在
任意一条指令之间插进来。理解这个区别，是后面写任何"能被打断的内核"的地基。

## 第 1 节　三条路径对比：调用 / 异常 / 中断

|  | 普通调用 | 异常 | 中断 |
|---|---|---|---|
| 入口 | `bl` | 硬件跳到 EENTRY | 硬件跳到 EENTRY（同一向量体系） |
| 触发 | 主动 | 执行流同步检测到 | 外设异步通知 |
| 返回 | `jr $ra` | `ertn`（回到 ERA 等） | `ertn` |
| 现场保存 | 调用约定内约定好的部分 | 入口需主动保存更多状态 | 通常保存得比异常更多 |
| 可屏蔽性 | — | 视类型而定 | 常可屏蔽 |

### 1.1 为什么不能把普通 C 函数地址直接当异常向量用

普通函数调用时，调用者和被调用者之间有一套"君子协议"（调用约定）：
哪些寄存器调用者负责保存、哪些被调用者负责保存，都是提前商量好的，因为双方
都是"自愿参与"这次调用的。

异常/中断完全不是这么回事：CPU 在执行任意一条指令的过程中被打断，
**打断发生的那一刻，几乎所有寄存器都可能正装着"半成品"的计算结果**，
而且被打断的代码根本不知道自己会被打断，也没有机会提前"收拾好现场"。
所以异常入口不能像普通函数那样只保存"调用约定要求的那一小部分"，
而必须由入口代码主动、完整地保存现场，处理完再原样恢复。

> **生活化类比**：普通函数调用像两个人提前约好"你去买菜，回来的时候
> 记得把发票给我"——分工清楚，互相知道对方会做什么。异常/中断更像
> 室友临时要借用你的书桌：他会先拍照记下你摊开的书本、笔的摆放
> （保存现场），然后去忙他自己的事（真正处理异常/中断），忙完再
> 照原样把书桌摆回去（恢复现场），你回来能接着写作业——全程你
> 自己毫不知情，也完全不用配合。

### 1.2 返回方式的差异：`jr $ra` vs `ertn`

`jr $ra` 是普通函数返回：跳回调用者保存在 `$ra` 里的地址，继续执行调用之后的代码，
这是软件层面的"君子协议"。

`ertn`（exception return）是硬件专门为异常/中断返回设计的指令：它不仅要跳转，
还要恢复处理器进入异常前的特权级、中断使能状态等硬件层面的运行模式，
这些是普通 `jr` 指令做不到的。**`ertn` 和 `jr $ra` 不能混为一谈**，
这也是讲义反复强调的一点。

## 第 2 节　`exception_entry` 逐行精读

```asm
exception_entry:
    addi.d      $sp, $sp, -32
    st.d        $ra, $sp, 24

    csrrd       $a0, 0x5          /* ESTAT */
    csrrd       $a1, 0x6          /* ERA */
    bl          exception_handler /* 返回值 $a0 = 处理函数给出的新 ERA */

    csrwr       $a0, 0x6          /* 写回 ERA，供 ertn 使用 */
    ld.d        $ra, $sp, 24
    addi.d      $sp, $sp, 32
    ertn
```

### 2.1 伸栈并保存 `$ra`

```asm
addi.d      $sp, $sp, -32
st.d        $ra, $sp, 24
```

因为接下来要 `bl` 到 C 函数 `exception_handler`，这一步和第 6 次课讲的
"非叶子函数需要先保存 `$ra` 再调用别的函数"是同一个道理——`bl` 会覆盖 `$ra`，
不提前存好，异常处理完之后就不知道该 `ertn` 回哪了。

### 2.2 `csrrd`：把控制状态寄存器读进通用寄存器

```asm
csrrd       $a0, 0x5          /* ESTAT */
csrrd       $a1, 0x6          /* ERA */
```

`csrrd`（CSR Read）把 CSR（控制状态寄存器，Control and Status Register）的内容
读到一个通用寄存器里。这里读了两个关键 CSR：

- **ESTAT**（Exception Status）：记录"这次异常是什么类型"（比如后面 Demo 里的
  `break` 指令触发的 `Ecode=0xC`）；
- **ERA**（Exception Return Address）：硬件自动记下的"触发异常那一刻，
  PC 停在哪条指令"。

按照函数调用约定，`$a0`、`$a1` 分别是第 1、第 2 个参数，所以紧接着
`bl exception_handler` 时，C 函数就能以 `exception_handler(estat, era)`
的形式拿到这两个值——这是"用汇编给 C 函数准备参数"的标准写法，
第 6 次课讲过的调用约定在这里被直接复用。

> **生活化类比**：`ESTAT` 和 `ERA` 就像事故现场的两块指示牌：一块写着
> "事故类型"（追尾/闯红灯/爆胎……），另一块写着"事故发生在哪个路口"。
> `csrrd` 就是交警到场后先把这两块牌子上的信息抄下来，作为处理报告的开头。

### 2.3 `bl exception_handler`：汇编怎么调用一个 C 函数

`bl` 指令本身只做两件事：把返回地址存进 `$ra`，然后跳转到目标符号的地址。
这里要跳去的 `exception_handler`，**并不是这份 `.S` 汇编文件里定义的标签**，
而是 `kernel/exception.c` 里用 C 写的一个函数。汇编代码怎么能直接跳进一段
C 代码里，还完美地把参数对上？——这要从"编译"和"链接"是两个独立步骤说起。

**第一步，汇编文件和 C 文件是分开翻译的。** `boot/start.S` 被汇编器翻译成一份
目标文件，`kernel/exception.c` 被编译器翻译成另一份目标文件。汇编器翻译到
`bl exception_handler` 这一行时，**并不知道这个函数具体在哪个地址**——它只能
在目标文件里留一条"占位"记录：这里将来要跳到一个叫 `exception_handler` 的符号。

**第二步，链接器负责把占位符号"对上号"。** 链接阶段，链接器把两份目标文件
拼在一起，发现 C 那边编译出来的目标文件里正好有一个同名符号
`exception_handler`（C 函数默认按原名导出符号，不会像 C++ 那样"改名"），
于是把 `bl` 指令里的占位地址回填成这个函数真正的地址。这一步做完，
`bl exception_handler` 才终于知道自己要跳到哪里。

**光对上地址还不够，双方还得"说同一种语言"。** 这就是第 6 次课讲过的
**调用约定**（LP64 ABI）在起作用：不管调用者是汇编写的还是 C 写的，
大家都遵守同一套规矩——参数依次放 `$a0`-`$a7`，返回值放 `$a0`，
`$ra` 存返回地址。正因为汇编代码和 C 编译器生成的代码遵守的是同一套规矩，
`exception_entry` 才能放心地先把 `$a0=ESTAT`、`$a1=ERA` 摆好，再 `bl` 过去：

- C 编译器给 `exception_handler(unsigned long estat, unsigned long era)`
  生成的函数体，一进来就知道该去 `$a0`、`$a1` 里取自己的两个参数——
  这两个寄存器名字和 C 代码里的形参 `estat`、`era` 完全对应；
- 函数执行到 `return era + 4;` 时，编译器会自动生成"把这个值放进 `$a0`，
  再 `jr $ra` 跳回去"的收尾代码——用的正是 `bl` 跳转那一刻自动存进 `$ra`
  的返回地址，也就是 `exception_entry` 里紧跟在 `bl` 后面那条
  `csrwr` 指令的位置。

所以整条链路是：`exception_entry`（汇编）把参数摆进 `$a0`/`$a1` → `bl` 跳进
`exception_handler`（C，经链接器牵线搭桥）→ C 函数用同样的寄存器取参数、
算出返回值放回 `$a0` → `jr $ra` 跳回 `exception_entry` 紧接着的那条指令
继续往下执行。全程没有人"翻译"或"转换"，靠的完全是双方共享同一套
寄存器摆放规矩。

> **生活化类比**：`bl exception_handler` 就像你在稿子里写"（详见附录 B）"——
> 写稿子的人（汇编器）不需要知道附录 B 印在第几页，排版时（链接阶段）
> 只要把"附录 B"这个名字和它实际所在的页码对上就行。你和附录 B 的作者
> （C 编译器）只要提前约好"材料按固定顺序摆放、结论写在固定位置"
> （调用约定），排版时就一定能接得上，谁都不用管对方内部是怎么写的。

### 2.4 `exception_handler` 的返回值：新的 ERA

```c
unsigned long exception_handler(unsigned long estat, unsigned long era)
{
    printk("[exception] ESTAT=0x");
    printk_hex(estat);
    printk(" ERA=0x");
    printk_hex(era);
    printk("\n");
    return era + 4;   /* break/syscall：跳过触发指令本身，见 §5 */
}
```

`exception_handler` 除了打印诊断信息，**还要返回一个新的 ERA 值**，
交给 `exception_entry` 用 `csrwr` 写回 CSR，供 `ertn` 使用。为什么要返回
`era + 4` 而不是原样返回 `era`？——这正是实验指导书 Task3 的"踩坑题"，
下一节专门讲。

### 2.5 恢复现场并 `ertn`

```asm
csrwr       $a0, 0x6          /* 写回 ERA，供 ertn 使用 */
ld.d        $ra, $sp, 24
addi.d      $sp, $sp, 32
ertn
```

`csrwr`（CSR Write）把 `exception_handler` 算出的新 ERA 写回 CSR，
然后恢复 `$ra`、恢复栈指针，最后 `ertn`——硬件会跳到"当前 CSR.ERA
所指的地址"继续执行，并恢复异常发生前的运行模式。

### 2.6 教学取舍：这只是最小骨架

真实系统的异常入口通常要保存**远不止 `$ra`** 这一个寄存器——因为处理函数
`exception_handler` 内部可能用到 `$a0`-`$a7`、`$t0`-`$t8` 等一大批
"调用者保存"寄存器，如果不在入口处把它们也存好，`exception_handler`
执行过程中悄悄改写了这些寄存器，被打断的代码恢复执行时就会发现自己的
计算结果莫名其妙变了。本课的 `exception_entry` 为了教学清晰，只保存了
`$ra` 这一个必需的寄存器，第 11 次课会把它原地升级为保存全部
caller-saved 寄存器的完整版本。

## 第 3 节　`era + 4` 踩坑题：为什么不能原样返回 `era`

### 3.1 精确异常与"指令重放"的直觉误区

`break`、`syscall` 这一类由指令本身主动触发的异常（区别于缺页这种"被动"异常），
硬件记录的 ERA **指向触发异常的那条指令本身**，而不是它的下一条。

直觉上你可能觉得"异常处理完了，当然要回到刚才中断的地方接着往下走"，
但如果原样把 `era`（也就是 `break` 指令自己的地址）写回去再 `ertn`，
CPU 会跳回**这条 `break` 指令本身**，然后立刻再次触发同一个异常——
于是陷入"触发异常 → 处理 → 返回原地 → 再次触发"的死循环，串口会不停
打印同一行诊断信息，程序再也走不到 `break` 之后的代码。

> **生活化类比**：这就像你在自动门前被感应器"卡"了一下（异常触发），
> 工作人员过来处理完，又把你放回了感应区正中央（原样返回 `era`）——
> 你前脚刚站稳，门的感应器又响了，处理完再被放回同一个位置……
> 陷入无限循环。正确做法是处理完之后把你往前挪一步，送到已经过了
> 感应区的位置（`era + 4`），你才能真正继续往前走。

### 3.2 为什么偏偏是 `+4`

本课程平台上每条指令固定占 4 字节，`era + 4` 就是"触发异常的这条指令的
下一条指令的地址"。`exception_handler` 返回 `era + 4`，相当于告诉硬件：
"这条引发异常的指令我已经处理完了，别再重新执行它，去执行它的下一条。"

### 3.3 亲手验证这个坑

实验指导书 Task3 特意要求：先把 `return era + 4` 改回 `return era`，
重新 `make run`，**亲眼看一遍死循环长什么样**，再改回来。这种"故意踩一次坑"
的练习，比单看文字描述更容易把"精确异常的 ERA 指向指令本身"这句话
刻进直觉里——以后遇到类似"处理完异常程序卡死不动"的故障，能第一时间
想到检查返回地址有没有正确跳过触发指令。

## 第 4 节　`exception_init`：告诉硬件"出事了去哪找人"

```c
void exception_init(void)
{
    unsigned long entry = (unsigned long)exception_entry;
    __asm__ volatile("csrwr %0, 0xc" : : "r"(entry) : "memory");
}
```

这段代码把 `exception_entry` 函数的地址写进 CSR `0xc`——也就是
**EENTRY**（Exception Entry，异常入口地址寄存器）。这一步必须在任何
异常可能发生之前完成，否则异常真的到来时，硬件"不知道该跳去哪里处理"，
后果通常是处理器进入更严重的错误状态或直接失控。

> **生活化类比**：`exception_init` 就像你入住酒店时，先在前台登记
> "如果客房里发生紧急情况，请打这个电话号码"。这个号码必须提前登记好，
> 真出事了火警铃一响，酒店才知道该联系谁；如果压根没登记过号码，
> 出事了也没人知道该往哪打电话。

具体的 CSR 编号（`0x5` ESTAT、`0x6` ERA、`0xc` EENTRY）**以课程讲义/手册为准**，
不同架构、不同教学平台的编号约定可能不同，不要凭空套用记忆中其他架构的数值。

## 第 5 节　中断：异常的"异步版本"

### 5.1 五个核心概念

| 概念 | 教学说明 |
|---|---|
| 中断源 | 定时器、UART 收等——谁发起了这次"打扰" |
| 中断使能 | 总开关 + 分源开关——两层开关都得打开中断才能真正响应 |
| 中断入口 | 与异常向量体系相关（本平台上与异常共用 EENTRY） |
| 上半部 | 入口尽快做完关键事，别把 CPU 长时间占在处理程序里 |
| 清源 / 应答 | 处理完必须"告诉"硬件这次中断已经处理，否则会反复触发 |

> **生活化类比**：中断使能的"总开关 + 分源开关"就像小区大门的总门禁
> 和每户房门的门禁——总门禁关了，任何一户的门禁开着也没用（外人进不了
> 小区）；总门禁开着，某一户自己把门锁上，那一户单独就不会被打扰。
> 两层开关必须都打开，这户的门铃才能真正响起来。

### 5.2 为什么"清源"这一步不能省

如果处理完一次中断，没有告诉硬件"这次中断我处理完了"，硬件会认为
这个中断源"还在喊"，于是同一个中断会被反复触发，处理程序陷入
"处理 → 立刻又被同一个中断打断 → 再处理"的循环，跟 §3 的 ERA 踩坑
在"忘了往前走一步"这个本质上是同一类错误——**只不过一个是忘了挪
返回地址，一个是忘了告诉硬件"这件事翻篇了"**。

> **生活化类比**：清源就像看完医生后一定要把候诊号"叫过"，不然
> 叫号系统会以为你还没被叫到，一直在屏幕上重复显示你的号码。

## 第 6 节　中断入口为什么比 `exception_entry` "更重"

```asm
interrupt_entry:
    addi.d  $sp, $sp, -256
    st.d    $ra, $sp, 0
    st.d    $a0, $sp, 8
    # ... 保存需要的寄存器 ...
    bl      interrupt_handler
    # ... 恢复 ...
    addi.d  $sp, $sp, 256
    ertn
```

### 6.1 关键区别：中断可能打在"任意一条指令之间"

`exception_entry` 处理的异常（如 `break`）是代码**自己**执行到某条指令时
主动触发的，触发的那一刻，编译器生成的代码本来就"恰好"处在一个相对
干净的状态。但中断是外部事件**随时**插进来的——可能恰好插在一段
正在密集使用十几个寄存器做计算的代码中间，这时候入口如果只保存
`$ra` 这一个寄存器，`interrupt_handler` 一执行，那些"正在计算到一半"
的寄存器内容就会被覆盖，中断返回后代码会得到面目全非的计算结果。

所以中断入口**不能对"调用约定"抱有任何假设**，必须把所有可能被
处理程序用到、又没有被调用约定保护的寄存器（`$ra`、`$a0`-`$a7`、
`$t0`-`$t8` 等）全部主动存下来。示意代码里的 `256` 字节这个数字本身
不重要，**"主动保存会被破坏的状态"这个原则才重要**。

> **生活化类比**：`exception_entry` 处理的情况像你自己主动按下了
> "暂停"按钮去接一个电话——你会本能地先把手头东西放稳当再接。
> 中断像有人从背后突然拍你的肩膀打断你——你手里正端着的、正写着的、
> 正算着的，全都可能因为这一下"愣神"而洒了、乱了，所以对方必须先
> 帮你把手里的一切原样定住，处理完了再原样还给你，绝不能假设
> 你被拍肩膀的瞬间刚好是"东西都放稳当"的状态。

### 6.2 第 11 次课的落地方式（预告）

本课程平台上，异常和中断实际共享同一个 `EENTRY`（不是分成两个独立入口），
所以第 11 次课的真实做法，不是像本节示意代码那样另建一个
`interrupt_entry`，而是把 `exception_entry` **原地升级**成保存全部
caller-saved 寄存器（`$ra`+`$a0`-`$a7`+`$t0`-`$t8`，共 144 字节）的完整版本，
让它同时安全地服务于异常和中断两种场景。本课先理解"为什么需要保存
更多现场"这个道理，具体落地留到第 11 次课的真代码里。

## 第 7 节　定时器 tick 最小故事线（纸面设计）

### 7.1 四个步骤

```text
1. 配置周期     —— 告诉定时器硬件"每隔多久响一次"
2. 使能中断     —— 打开总开关和定时器这一路的分开关
3. 处理函数     —— ticks++，必要时 printk，最后清中断源
4. 主循环 idle  —— 主循环可以安静等待，靠中断把它"叫醒"
```

> **生活化类比**：定时器 tick 像厨房里的烤箱定时器：先设定"每 20 分钟响一次"
> （配置周期），按下启动键（使能中断），响铃后有人去看一眼、记一笔
> "第几次响铃了"、按掉铃声（处理函数：计数 + 清源），中间该干嘛干嘛，
> 不用一直守在烤箱前傻等（主循环 idle）。

### 7.2 `ticks` 与 `.bss` 清零的关系

`ticks` 通常是一个全局变量，如果处理函数写的是 `ticks++`（先读后写），
而 `ticks` 又没有被显式初始化，它就落在 `.bss` 段——这正是第 2 次课讲过的
"未初始化的全局/静态变量，必须依赖 `.bss` 段在启动阶段被清零，否则初值
是一堆随机的历史内存内容"。如果 `.bss` 没清零，`ticks` 的计数会从一个
不可预测的随机值开始递增，打印出来的次数完全没有意义。这也是本课
和第 2 次课知识点的一次直接呼应。

### 7.3 完整例子：把 tick 真正接起来（含真实 CSR 编号）

上面两小节讲的是"纸面设计"，这里给一个**首尾完整、CSR 编号真实**的例子，
让"配置→使能→处理→清源"这四步不再是抽象名词。除了已经学过的
ESTAT(0x5)、ERA(0x6)、EENTRY(0xc)，中断还要用到三个新 CSR：

| CSR | 编号 | 作用 |
|---|---|---|
| **CRMD** | 0x0 | `IE` 位（第 2 位）：全局中断**总开关** |
| **ECFG** | 0x4 | `LIE` 位域：每个中断源的**分开关**，定时器对应第 11 位 |
| **TICLR** | 0x44 | 定时器中断**清源**：写 1 到 `TI` 位（第 0 位）即可清除 |

这三个和 §5.1 表格里"中断使能""清源/应答"两个概念是一一对应的关系：
`CRMD.IE` + `ECFG.LIE` 就是那"两层开关"，`TICLR` 就是"清源"的具体操作。

**第一步：使能（对应 §5.1 的总开关 + 分开关）**

```c
/* 打开分开关：ECFG.LIE 的第 11 位（定时器这一路） */
unsigned long ecfg;
__asm__ volatile("csrrd %0, 0x4" : "=r"(ecfg));
ecfg |= (1UL << 11);
__asm__ volatile("csrwr %0, 0x4" : : "r"(ecfg));

/* 打开总开关：CRMD.IE */
unsigned long crmd;
__asm__ volatile("csrrd %0, 0x0" : "=r"(crmd));
crmd |= (1UL << 2);
__asm__ volatile("csrwr %0, 0x0" : : "r"(crmd));
```

逐行拆解：

- **先 `csrrd` 再 `csrwr`，而不是直接写一个新值**：ECFG 这个 CSR 里不只有定时器这一位，还挤着其他中断源的开关位。如果不先读出来、直接写一个只含"第 11 位是 1"的数进去，会把其他本来已经打开的开关全部误关掉。所以固定套路是"读出来 → 只改需要的那一位 → 写回去"，CRMD 同理。
- `csrrd %0, 0x4` 把 ECFG（编号 0x4）当前的完整内容读到变量 `ecfg`——语法和 §4 `exception_init` 里的 `csrwr %0, 0xc` 是同一套内联汇编写法：`%0` 对应后面 `: "=r"(ecfg)` 里的 `ecfg`，意思是"执行这条 CSR 指令，把结果放进这个 C 变量"。
- `ecfg |= (1UL << 11)` 是纯 C 语言的位运算：`1UL << 11` 算出一个只有第 11 位是 1、其余全是 0 的数，`|=` 把这一位"点亮"，同时保证其他位原样不动——这一步不涉及汇编，是在 C 变量上做修改。
  - **`1UL` 是什么**：`1` 后面的 `U` 表示 `unsigned`（无符号），`L` 表示 `long`（长整型），合起来是告诉编译器"把这个 `1` 当成 `unsigned long` 类型"，而不是默认的 `int`。`ecfg`/`crmd` 都是 `unsigned long`（64 位），如果写成普通的 `1 << 11`，`1` 默认是 32 位 `int`，本例中移位 11 位不会出问题，但如果将来要移到第 32 位以上（某些 CSR 的高位标志），32 位 `int` 会直接装不下、发生错误。写成 `1UL` 从一开始就是 64 位宽，移多少位都安全，是操作 CSR 位掩码时的防御性写法。
- `csrwr %0, 0x4` 把改好的新值写回 ECFG，定时器这一路的分开关就算打开了。
- 下面 `CRMD.IE` 那四行是完全一样的套路：读出 CRMD 当前值 → 只把第 2 位（`IE`，全局中断总开关）改成 1 → 写回去，对应的就是总开关。

**内联汇编语法拆解：`__asm__ volatile("csrrd %0, 0x4" : "=r"(ecfg));`**

这一整行是 GCC 的"内联汇编"写法，作用是在 C 代码中间直接嵌入一条汇编指令。拆成几块看：

```text
__asm__ volatile ( "csrrd %0, 0x4"  :  "=r"(ecfg)  ) ;
   │        │            │              │
  关键字   修饰符      汇编模板        输出操作数列表
```

- **`__asm__`**：告诉编译器"接下来这一段不是 C 代码，是汇编指令"，是 GCC 提供的关键字（`asm` 是它的别名，写法一样）。
- **`volatile`**：禁止编译器优化掉这条汇编——如果不加，编译器可能觉得"这条指令的结果没人用"就把它删了（呼应 §1.2 讲过的 volatile 原理，只是这里保护的是一整条指令，不是某个内存地址）。
- **`"csrrd %0, 0x4"`**：**汇编模板**，也就是真正要执行的指令，写在字符串里。`0x4` 是 CSR 编号（ECFG），直接照抄；`%0` 是一个"占位符"，不是真的写"`$a0`"这种具体寄存器名——**具体用哪个寄存器，交给编译器自己去决定**。
- **冒号 `:`**：内联汇编用冒号把"模板"和后面几部分隔开，完整格式是
  `汇编模板 : 输出操作数 : 输入操作数 : 会被破坏的寄存器`。这一行只写了一个冒号，说明只用到"输出操作数"这一段，后面的输入、clobber 都留空。
- **`"=r"(ecfg)`**：**输出操作数**。`(ecfg)` 表示"结果最终要放进 C 变量 `ecfg` 里"；`"=r"` 是给编译器的约束提示——`=` 表示"这是一个只写的输出"，`r` 表示"帮我挑一个通用寄存器来装这个值"。合起来就是："这条指令执行完，找一个寄存器装结果，然后把那个寄存器的值存进 `ecfg`"。
- **`%0` 和 `"=r"(ecfg)` 是怎么对上的**：`%0` 指的是操作数列表里第 0 个操作数，而 `"=r"(ecfg)` 正是唯一的（也就是第 0 个）操作数。所以编译器会把 `%0` 替换成它挑的那个寄存器——最终生成的真实指令可能是 `csrrd $t0, 0x4`（具体用哪个寄存器由编译器决定，不是你写死的）。

整句话翻译成人话就是："执行 `csrrd` 指令去读编号 `0x4` 的 CSR，随便找个寄存器接住结果，然后把这个结果放进 C 变量 `ecfg`。"后面 `csrwr %0, 0x4" : : "r"(ecfg)` 那一行结构完全对称，只是这次 `"r"(ecfg)` 前面没有 `=`，说明这次 `ecfg` 是**输入**（把它的值送进 CSR），而且这个操作数出现在第二个冒号后面（输入操作数的位置），不是第一个。

**第二步：处理（在 `exception_handler` 里加一条分支）**

第 6.2 节说过，本平台异常和中断共享同一个 `EENTRY`，所以不需要另外的
`interrupt_handler`——只需要在原来的 `exception_handler` 最前面，
先看 `ESTAT` 的低 13 位（`ESTAT.IS`）有没有对应的中断号亮着：

```c
unsigned long exception_handler(unsigned long estat, unsigned long era)
{
    unsigned long is = estat & 0x1fffUL;   /* ESTAT.IS[12:0]：哪些中断在响 */

    if (is & (1UL << 11)) {                 /* 第 11 位 = 定时器中断 */
        ticks++;
        if (ticks % 100 == 0)
            printk("tick\n");

        unsigned long one = 1;
        __asm__ volatile("csrwr %0, 0x44" : : "r"(one));  /* 清源：TICLR.TI 写 1 */

        return era;              /* 注意：这里不能 +4，见下文 */
    }

    /* 走到这里说明是第 2-4 节讲过的同步异常（break/syscall），逻辑不变 */
    printk("[exception] ESTAT=0x");
    printk_hex(estat);
    printk(" ERA=0x");
    printk_hex(era);
    printk("\n");
    return era + 4;
}
```

**第三步：为什么这里不能 `+4`——和 §3 正好相反的坑**

§3 讲过，`break`/`syscall` 这类**精确异常**的 ERA 指向触发指令本身，
所以要 `+4` 跳过去，不然会原地死循环。但**中断是异步事件**，它插在
"两条指令之间"，ERA 记录的是**还没来得及执行、被打断的那一条指令**。
处理完中断应该让程序**原样继续执行这条指令**，而不是跳过它——
如果照搬 `era + 4`，会凭空丢掉一条本该执行的指令，程序会出现
莫名其妙的错误结果。

> **生活化类比**：这就像有人正在朗读一段话，读到一半被人插话打断。
> 插话说完，朗读者应该**从刚才被打断的那个字接着念**，而不是跳到
> 下一个字——因为那个字他压根还没来得及念出口。这和"精确异常要
> `+4`"正好相反：`break` 指令是"已经执行完才触发异常"，要跳过去；
> 中断是"还没执行完就被打断"，必须原样回来接着念。

**四步对照速查**：

```text
①配置周期    → TCFG 配置定时器（第 11 次课上机实现，本课不展开）
②使能中断    → ECFG.LIE 第11位 + CRMD.IE（上面代码）
③处理函数    → exception_handler 里判断 ESTAT.IS 第11位，ticks++/printk
④清源        → 写 1 到 TICLR.TI，同时 return era（不是 era+4）
```

## 第 8 节　并发与临界区：中断打断主循环的风险

### 8.1 字符交错问题

如果主循环也在 `printk`，中断处理函数里恰好也在 `printk`，
两边同时写同一个 UART，就会出现"你一个字符我一个字符"交叉打印的
乱码——这正是第 8 次课思考题"两个执行流同时 `printk` 会怎样"的
一个具体实例：中断处理函数就是这样一个"随时可能插进来的执行流"。

### 8.2 关中断保护共享数据（教学点到为止）

本课对策是"短时间关闭中断，操作完共享数据再打开"，本质上是把一小段
代码变成"这段时间内绝对不会被打断"的临界区。本课只要求理解这个思路，
不要求实现真正的锁机制（后续课程会展开）。

> **生活化类比**：关中断像你在数一沓现金的时候，先把房门反锁——
> 这段时间任何人敲门你都不开，数完了再开锁。时间不能锁太久
> （门锁太久别人一直进不来，等同于"中断处理要尽量短"这条原则），
> 但数钱的过程中绝对不能被打断，不然很容易数错。

## 第 9 节　小结：本课新增的心智模型

1. **打断分两种**：同步异常（自己触发）、异步中断（外部通知），
   二者共享同一套硬件跳转机制，但对"现场保存"的要求不同。
2. **`ertn` ≠ `jr $ra`**：前者是硬件级的异常返回，会恢复运行模式；
   后者只是软件约定的普通函数返回。
3. **精确异常的 ERA 指向触发指令本身**：处理完常需要 `+4` 才能真正前进，
   不然会原地死循环。
4. **EENTRY 必须提前登记**：否则异常/中断真的发生时硬件"无处可去"。
5. **中断入口更重**：不能假设调用约定现场完整，要主动保存更多寄存器。
6. **清源不可省**：处理完不告诉硬件"翻篇了"，会导致同一中断反复触发。
7. **`ticks` 依赖 `.bss` 清零**，中断与主循环共享资源需要临界区保护。
